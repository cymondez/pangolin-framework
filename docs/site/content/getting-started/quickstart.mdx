這一頁會帶你寫出第一個真正由 panGOlin Runtime 驅動的 Go 應用：我們只定義一個最小的 `hello` 模組，交給 `app.Run` 啟動、印出訊息，並在 1 秒後自動優雅停機。

---

## 為什麼不直接在 `main()` 裡寫 `fmt.Println`？

如果程式真的只有一行 `fmt.Println`，當然不需要框架。但實務專案很快就會同時需要：
- 多個功能模組按相依順序啟動（例如先連資料庫，再啟動業務服務，最後開啟 HTTP Port）。
- 收到關閉訊號時，反序釋放所有資源而不丟失進行中的請求。
- 在任何資源啟動前先統一驗證設定與服務依賴。

panGOlin 把這整套骨架收斂成一個極簡入口：**定義 Module struct → 交給 `app.Run(ctx, root)`**。這個最小範例就是要讓你先看懂這個核心骨架，完全沒有多餘雜訊。

### 逐段導讀：每一段程式碼的作用

1. **`type helloModule struct { module.Base }`**（步驟 1）
   - 在 panGOlin 中，**模組就是一個普通的 Go struct**，不需要繼承複雜的基底類別，也不需要靠魔法註解掃描。
   - 嵌入 `module.Base` 可以直接幫你實作 `ModuleMetadata()`，提供模組的 `Name`（唯一識別名）與 `Version`（供其他模組宣告版本約束使用）。
2. **`func (m *helloModule) Start(context.Context, module.Runtime) error`**（步驟 2）
   - `Start` 是可選的生命週期方法（其他還有 `PreConfigure`、`Configure`、`PostConfigure`、`Stop`，用不到就不用寫）。
   - 當 Runtime 驗證完所有模組與設定後，就會按相依順序呼叫每個模組的 `Start`。如果回傳非 `nil` 錯誤，應用會立即中止啟動並自動回收已建立的資源。
3. **`ctx, stop := context.WithTimeout(...)`**（步驟 3）
   - `app.Run` 是**阻塞式**的：所有模組啟動完成後，它會持續等待直到 `ctx` 被取消或逾時。
   - 正式的 HTTP 伺服器或背景 Worker 會改用 `signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`，讓程式常駐運行直到收到停止訊號；這裡為了讓命令列教學能自動結束，刻意用 1 秒逾時模擬收到停機訊號。
4. **`app.Run(ctx, root)`**（步驟 4）
   - 這是 panGOlin 推薦的 **Root 裝配入口**。你只需要把最頂層的根模組交給它，它就會自動完成：內建必要預設值（包含 UOW 預設逾時）→ 收集相依模組 → 組態與 DI 封存 → 啟動 → 等待 `ctx` 結束 → 反序停機。

## 3. 動手驗證：修改輸出訊息

找到 `Start` 方法中的 `fmt.Println`，改成自己的訊息：

```go title="修改 Start 方法"
func (m *helloModule) Start(context.Context, module.Runtime) error {
	fmt.Println("Hello, my application!")
	return nil
}
```

再次執行 `go run .`，確認終端機印出 `Hello, my application!`。

## 常見疑問（新手 FAQ）

- **為什麼程式印出訊息後停頓了約 1 秒才結束？**
  因為 `Start` 完成後應用已經進入「運行中（Ready）」狀態，正在等待 `ctx` 結束；1 秒期限一到，`app.Run` 才觸發停機流程並正常返回。
- **如果不小心把 `Name` 留空會發生什麼事？**
  你可以試著把 `Name: "hello"` 改成 `Name: ""` 再執行一次——`app.Run` 會在任何 `Start` 執行前就直接拒絕並回報明確的模組驗證錯誤。這是 panGOlin「寧可在啟動第 0 秒失敗，也不讓錯誤帶進運行期」的核心原則。
