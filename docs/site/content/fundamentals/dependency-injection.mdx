依賴注入（DI）讓你的業務程式接收需要的服務，而不是到處自行建立服務。Root 裝配的預設做法：模組在 `Configure` 以建構子註冊服務，Start 之後透過受限 resolver 解析。

## 執行範例

從套件來源的 `examples/basics` 執行：

```bash
go run ./root-greeting
```

預期輸出 `Hello, World!`（設定 `APP_NAME=Reader` 後為 `Hello, Reader!`）。完整程式見[問候服務教學](../tutorials/greeting-application.mdx)：

<CodeBlock language="go" title="examples/basics/root-greeting/main.go">{source}</CodeBlock>

## 如何使用

1. 在 `Configure` 用 `b.Services().Add(NewGreetingService, module.Singleton())` 註冊建構子；解析鍵就是建構子的精確回傳型別。
2. 省略生命週期選項時預設為 Transient：每次解析建立新物件。
3. `Start` 之後用 `rt.Services().Resolve(ctx, module.Contract[*GreetingService]())` 取得服務；`module.Contract[T]()` 由 T 的完整型別身分推導出鍵，介面與具象型別皆可用。
4. 服務清理（Cleanup）由組合容器在應用收尾時執行；你只在自己的資源確實需要關閉時才回傳 Cleanup。

建構子參數會自動解析：`NewService(s *store.Store)` 的 `*store.Store` 若已由自己的模組或直接相依模組提供，直接寫在參數上即可。重複、缺漏或循環在任何建構子執行前就失敗，不會啟動出半套的應用。

## 選擇存活期間

| 選項 | 何時使用 |
|---|---|
| 預設（Transient） | 每次取得都要建立新物件 |
| `module.Singleton()` | 整個應用共用的服務，例如可安全並行使用的連線池 |
| `module.Operation()` | 同一次操作共用，操作結束即清理 |

Operation 服務只能經明示操作範圍解析：在 Start／Stop 內呼叫 `module.OpenScope(ctx, rt.Services())` 取得屬於這個模組的 scope，透過 `scope.Resolve` 取得服務，最後由呼叫端 `scope.Close`（清理只做一次，重複呼叫無害）。Singleton 不能保留 Operation 服務，避免跨請求共用本來應該隔離的狀態。

## 跨模組介面契約

同一模組內以具象型別為鍵就夠了。要讓**其他模組**使用你的服務時，把介面放進可 import 的 contracts 套件，並由擁有契約的模組單一負責 `Export`；消費模組直接相依該擁有者模組，再從自己的受限 resolver 解析契約。以下是可執行的正式示範 `examples/moduleapp` 的完整原始檔：

在套件來源的 `pangolin-framework/examples/moduleapp` 執行：

```bash
go run .
```

預期輸出（按 Ctrl+C 結束，可看到同樣的反序停機；非互動環境先設定 `MODULEAPP_DEADLINE=2s`）：

```text
planned layers:
  0: [store]
  1: [catalog pricing]
  2: [app]
start store (shared instance 0)
start catalog via *catalog.Service: demo/true="root-composed"
start pricing via *pricing.Prices: 12.00 EUR
start app: catalog ready with 1 entry via *catalog.Service
stop app
stop pricing
stop catalog
stop store
```

要點：

- 每個介面契約只有一個擁有者；Export 集中在擁有者模組的 `Configure`。
- 其他模組提供替代實作時以 `module.As(contract)` 明示貢獻，且必須直接相依契約擁有者；結構上滿足介面本身不會自動跨模組公開。
- 沒有 Export 的服務對其他模組不可見：此示範中 `*Prices` 只有 pricing 模組自己能解析。
