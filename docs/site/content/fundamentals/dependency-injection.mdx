## 為什麼需要受控的依賴注入？

在一般 Go 專案裡，手動在 `main.go` 裡一層一層 `NewA(NewB(NewC(db)))` 起初很直覺，但跨過 5 個模組之後就會出現三個問題：

1. **接線爆炸與資源洩漏**：誰建立連線池、誰負責 `Close()`、關閉順序跟建立順序是否相反，全靠人工記憶。
2. **存活期誤用（Captive Dependency）**：不小心把「單次請求專用（帶有 Request 狀態）」的物件存進「全域共用（Singleton）」服務的欄位裡，造成併發競爭與跨請求資料汙染。
3. **跨模組邊界失守**：A 模組直接去拿 B 模組的內部實作 struct，一旦 B 想重構內部實作，整個專案一起壞掉。

panGOlin 的 DI 設計結合了 Go 的簡潔與嚴格邊界：
- **一般 Go 建構子直接註冊**：你寫的 `NewService(s *store.Store) *Service` 不需要加任何框架 struct tag，引擎透過參數型別自動解析注入。
- **啟動前一次封存（Seal）**：重複註冊、缺漏依賴、循環依賴、以及「Singleton 誤捕獲 Operation 服務」，全部在任何建構子執行前就靜態攔截。
- **預設私有，顯式公開（Export）**：未呼叫 `Export` 的服務只有自己模組看得見，徹底守住模組封裝。

### 註冊與解析的 4 個核心規則

1. **建構子就是一般函式**：支援三種簽名——`func(...) T`、`func(..., error)` 或 `func(...) (T, func(context.Context) error, error)`（第二回傳值為 `Cleanup` 函式）。建構子參數可選擇接收最多一個 `context.Context`，其餘參數皆自動從 DI 解析。
2. **用高階輔助函式指定存活期**：
   - `module.AddSingleton(b.Services(), NewSvc)`：全應用單例共用。
   - `module.AddTransient(b.Services(), NewSvc)`：每次解析建立新實例（省略選項時的預設值）。
   - `module.AddOperation(b.Services(), NewSvc)`：綁定單次操作 Scope，操作結束即清理。
   - 若要讓建構子同時貢獻給另一個模組的介面契約，加上 `module.As(module.Contract[MyInterface]())` 選項即可。
3. **解析鍵 = 建構子的精確回傳型別**：建構子必須回傳具象型別（如 `*GreetingService`），不可直接回傳介面；這樣能明確區分「實作擁有權」與「契約公開權」。
4. **用泛型 `module.Resolve[T]` 型別安全解析**：在 `Start` 或操作 Scope 內一律使用 `module.Resolve[*GreetingService](ctx, rt.Services())`（或 `module.Resolve[contracts.Catalog](ctx, scope)`），不需要自己做 `any` 轉型。

> **Cleanup 自動化**：若你的建構子回傳了 `Cleanup` 函式（例如關閉連線池或檔案），容器會在應用停機（或 Operation Scope `Close`）時依反序自動呼叫，不需要再於 `Module.Stop` 重複關閉。

## 2. 正確挑選存活期間（Lifetime）

挑錯存活期是 DI 新手最容易埋下併發 Bug 的地方。請依下表判斷：

| 存活期 | 建立時機與共用範圍 | 適用範例 | 嚴格限制與防呆 |
|---|---|---|---|
| **Singleton** (`AddSingleton`) | 封存後全應用共用同一份實例，停機時清理 | 無狀態 Application Service、執行緒安全的 DB Pool、設定讀取器 | **禁止依賴 Operation 服務**（包含間接透過 Transient 依賴），Seal 階段直接拒絕，防堵 Captive Dependency。 |
| **Transient** (`AddTransient` / 預設) | 每次解析都建立全新物件 | 輕量無狀態計算器、一次性組裝工具 | 不可假設多次解析拿到同一指標。 |
| **Operation** (`AddOperation`) | 每次呼叫 `rt.OpenScope(ctx)` 建立一份，在該 Scope 內共用，`scope.Close(ctx)` 時清理 | 單次請求／任務專用的工作緩衝、短生命週期資源 | **禁止直接從根 Resolver 解析**，必須透過明確開啟的 `scope` 取得並由呼叫端 `defer scope.Close(ctx)`（重複 Close 安全無害）。 |

```go title="正確使用 Operation Scope 範例 ✅"
func (m *Module) Start(ctx context.Context, rt module.Runtime) error {
	// 1. 透過 rt.OpenScope 開啟綁定本模組身分的 Operation Scope
	scope, err := rt.OpenScope(ctx)
	if err != nil {
		return err
	}
	// 2. 確保操作結束時釋放所有 Operation 服務（Cleanup 有界且冪等）
	defer scope.Close(ctx)

	// 3. 從 scope 解析 Operation 或公開契約服務
	svc, err := module.Resolve[contracts.Catalog](ctx, scope)
	if err != nil {
		return err
	}
	_ = svc
	return nil
}
```

> **安全保證**：`rt.OpenScope(ctx)` 建立的 Scope 會鎖定建立當下的模組擁有者身分，絕不會洩漏底層封存容器（Sealed Container）或繞過模組可見性檢查。（早期 `module.OpenScope(ctx, rt.Services())` 僅作過渡保留，新程式請直接使用 `rt.OpenScope(ctx)`。）

## 3. 跨模組介面契約：如何安全地讓別人呼叫你？

同模組內直接用 `*MyService` 具象型別註冊就夠了。當 **模組 A（`app`）** 需要呼叫 **模組 B（`catalog`）** 的能力時，panGOlin 有一套非常清楚的可見性規則：

```text
[ module: catalog ]                           [ module: app ]
  ├─ 內部實作 *catalog.Service（預設私有）       ├─ DependsOn: [catalog, pricing]
  ├─ Export(contracts.Catalog)  ──────────────▶ ├─ ✅ 可解析 contracts.Catalog
  └─ 依賴 store.Module                          └─ ❌ 無法解析 *pricing.Prices（未 Export）
```

### 跨模組契約的四條鐵律

1. **單一擁有者原則**：每個介面契約在全應用中**只能有一個模組呼叫 `Export`**，避免多個模組互相搶奪契約定義權。
2. **必須直接相依**：消費模組必須在 `DependsOn()` 明示直接相依契約擁有者，才看得到該契約；間接（傳遞）相依不會自動透傳可見性。
3. **顯式貢獻才算候選**：如果另一個模組想為某契約提供替代實作，必須直接相依該契約擁有者，並在註冊時明示 `module.As(module.Contract[MyContract]())`；**單純在 Go 語法上實作了相同方法，不會自動變成跨模組公開實作**。
4. **替換必須留紀錄**：使用 `Replace`／`ReplaceBinding`／`ReplaceContract` 抽換實作時必須提供非空 `reason` 字串，框架會保留完整替換來源紀錄，杜絕「不知哪裡默默把實作覆蓋掉」的除錯惡夢。

## 常見反例對照

- **❌ 反例：建構子直接回傳介面 `func NewService() contracts.Catalog`**
  Seal 階段會直接拒絕。**✅ 正確做法**：建構子回傳具象型別 `*Service`，再由契約擁有者呼叫 `b.Services().Export(module.Contract[contracts.Catalog]())`。
- **❌ 反例：在 Singleton 服務裡保存 Operation 服務，或用 `MustResolve` 寫在正式 `Start` 裡**
  Singleton 捕獲 Operation 會被 Seal 直接拒絕；正式程式碼應使用回傳 `error` 的 `module.Resolve[T]`（`module.MustResolve[T]` 僅供測試 fixture 使用）。
